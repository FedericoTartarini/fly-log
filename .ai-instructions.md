## Project Overview

- React + Vite SPA for visualizing personal flight data using Mantine components, D3 for globes, and Firebase for storage.
- Frontend is TypeScript-ready but currently uses `.jsx`/`.tsx` mostly in `src/`; keep component logic focused in `src/pages`, `src/components`, shared utils under `src/utils`, and state in `src/store.ts` (Zustand).
- Data enrichment comes from hosted JSON assets (e.g., `assets/world-fallback.json`) and Firebase flight documents with `departure_date`, `departure_time`, IATA codes, and coordinates.
- Global state lives centrally in the Zustand store (`src/store.ts`). Pages/components should read from that store instead of managing their own copies of flight/filter state; use selectors or `useFlightStore` hooks to access `allFlights`, `filteredFlights`, filters, etc.

## Development Workflow

- Run scripts via `npm`. Main commands: `dev`, `build`, `lint`, `vitest`, `test:e2e`.
- Testing uses Vitest + Testing Library; shared wrapper in `test-utils/render.jsx` wraps Mantine `MantineProvider env="test"`.
- Avoid running destructive git commands; inspect `git status` before modifying.

## Styling & UI Guidelines

- Use Mantine components for layout and controls; prefer expressive typography and intentional color choices, avoiding vanilla system fonts (Inter, Roboto).
- Do not use CSS in the project.
- For D3 visualizations: keep globe animation logic within page component, reuse helpers (e.g., `buildArcCoordinates`, `getRouteMidpoint`). Always clean up transitions/observers on unmount.

## Code Conventions

- Prefer `React.useMemo`/`useEffect` for derived data or side effects. Keep intensive calculations memoized and watchers dependency arrays accurate.
- Use helper utilities in `src/utils` (e.g., `dateUtils`, `airportUtils`) for parsing dates, geolocations, and mapping IATA to cities. Use TypeScript where helpers already typed.
- Sorting/filtering should rely on `parseToDate` + time combos as needed (e.g., combine `departure_date` with `departure_time` for ordering). Always guard against invalid coordinates or missing fields.
- When a constant (filters, scopes, etc.) is shared across files, define it once (preferably as `as const`) and import the value instead of hard-coding strings. Example:

  ```ts
  export const TIME_GROUPING = {
    DAY_OF_WEEK: "dayOfWeek",
    YEAR: "year",
    MONTH: "month",
  } as const;
  ```

  This ensures consistent values and enables TypeScript inference where the constant is used.

## Testing/Assertions

- In Vitest tests, mock data (like D3 `json`) and set store state directly (`useFlightStore.setState`). Use `render` from `test-utils` to ensure Mantine context; use `userEvent` for interactions and `waitFor` for async UI/promise-driven effects.
- Check translated strings from `public/locales/{en,it}/tour.json` when asserting UI text (e.g., `Start animation`, `From year`).

## Known Artifacts

- Airport lookup uses `src/utils/referenceData.ts` with cached maps; `getAirportCity` returns sanitized city names.
- Flights stored in `useFlightStore` (Zustand) contain `allFlights`, `filteredFlights`, filters object; use selectors in pages.
- `WorldTour` sorts routes by `date` (now includes departure time) and filters by year range/past/future/overall. There are `scope` controls plus `from`/`to` selects for range filtering.
